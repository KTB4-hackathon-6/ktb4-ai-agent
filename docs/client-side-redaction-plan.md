# 브라우저 내 계약서 민감정보 자동 가림 구현 계획

## 1. 목적

사용자가 선택한 근로계약서 원본을 서버나 외부 OCR 서비스에 보내기 전에 브라우저에서
민감정보를 탐지하고 제거한다. 서버에는 분석에 필요한 계약 조건만 남은 새 이미지 파일만
전송한다.

이 계획의 핵심 보장은 다음과 같다.

- 사용자가 가림 결과를 확인하기 전에는 분석 세션 생성과 파일 업로드를 시작하지 않는다.
- 원본 `File`, 원본 파일명, PDF 텍스트 레이어와 이미지 메타데이터를 서버에 보내지 않는다.
- 자동 탐지는 후보를 제안하고, 최종 전송 여부는 사용자가 페이지별로 확인한다.
- OCR 실패나 브라우저 자원 부족 시 원본 업로드로 우회하지 않고 수동 가림으로 전환한다.

## 2. 현재 상태와 변경 범위

현재 `frontend/src/components/chatbot/ContractFlow.tsx`는 파일을 선택하면 즉시
`onStartAnalysis(files)`를 호출한다. `frontend/src/api/contracts.ts`는 받은 원본 파일을
그대로 `FormData`의 `files` 파트에 넣어 Spring으로 전송한다.

이번 변경은 이 두 단계 사이에 브라우저 redaction 단계를 추가한다.

```text
현재
파일 선택 → 원본 FormData 생성 → 서버 OCR·분석

변경 후
파일 선택
  → 브라우저 페이지 변환
  → 브라우저 OCR
  → 민감정보 후보 생성
  → 사용자 검토
  → 픽셀 가림 및 새 파일 생성
  → 가공본 FormData 생성
  → 서버 OCR·분석
```

Spring과 FastAPI API 계약은 변경하지 않는다. Spring은 이미 JPEG, PNG와 여러 `files`
파트를 받으므로 PDF를 페이지별 이미지로 바꾼 결과를 그대로 처리할 수 있다.

## 3. 범위

### 포함

- JPEG, PNG, PDF의 브라우저 내 페이지 변환
- 한국어와 영문이 섞인 문서의 로컬 OCR
- 정규식 및 필드 라벨 기반 민감정보 후보 탐지
- 후보 선택·해제와 수동 영역 추가·수정
- 불투명 픽셀 가림, 파일명 익명화 및 이미지 재인코딩
- 가공본 재검사 후 기존 계약 분석 API 호출
- 모바일, 키보드 조작, 한국어·영어 안내
- 탐지 규칙 단위 테스트와 실제 브라우저 네트워크 검증

### 제외

- 서버 측 원본 보관 또는 서버 측 원본 redaction
- 완전 자동 업로드
- 범용 NER 모델이나 문서 서식별 좌표 템플릿
- 가림 처리된 PDF 재생성
- 얼굴, 도장, 서명의 자동 이미지 인식
- Admin 데모 업로드 흐름 변경

범용 NER와 서식별 템플릿은 실제 평가 문서에서 라벨 기반 탐지의 누락률이 문제로 확인될
때만 추가한다.

## 4. 민감정보 정책

### 기본 가림 대상

| 종류 | 자동 탐지 방법 | 기본 선택 | 비고 |
|---|---|---:|---|
| 주민·외국인등록번호 | 숫자 형식 + 주변 라벨 | 예 | OCR의 공백·하이픈 혼동을 허용한다. |
| 전화번호 | 국내·국제 전화 형식 | 예 | 금액과 혼동하지 않도록 구분자를 확인한다. |
| 이메일 | 이메일 형식 | 예 | 형식 일치만으로 탐지한다. |
| 근로자·사업주 이름 | `성명`, `Name`, `근로자`, `사업주`, `대표자` 인접 값 | 예 | 이름 자체를 사전으로 판별하지 않는다. |
| 주소 | `주소`, `Address`, `소재지` 인접 값 | 예 | 같은 행과 바로 다음 행까지만 포함한다. |
| 여권번호 | `여권`, `Passport` 인접 영숫자 | 예 | 전역 영숫자 패턴으로 찾지 않는다. |
| 계좌번호 | `계좌`, `Account`, `은행` 인접 숫자 | 예 | 임금과 혼동하지 않도록 라벨 인접 시에만 탐지한다. |
| 생년월일 | `생년월일`, `Date of birth`, `DOB` 인접 날짜 | 예 | 계약 시작·종료일은 가리지 않는다. |

### 수동 확인 대상

- 손글씨 이름과 주소
- 서명, 지문, 얼굴 사진, 도장
- 흐리거나 일부가 가려진 번호
- 표 밖에 별도로 기재된 개인정보

### 분석을 위해 유지할 정보

- 계약 시작일과 종료일
- 급여, 수당, 공제액과 지급일
- 근로시간, 휴게시간과 휴일
- 업종, 업무 내용과 숙식 제공 조건

일률적으로 모든 날짜와 긴 숫자를 가리면 계약 분석에 필요한 값까지 사라지므로 사용하지
않는다.

## 5. 상세 처리 흐름

### 5.1 파일 선택과 네트워크 차단

파일 선택 직후에는 `File[]`을 redaction 화면의 메모리 상태에만 보관한다. 이 시점에는
`analyzeContract()`를 호출하지 않으므로 `POST /api/sessions`도 발생하지 않는다.

다음 동작은 금지한다.

- 원본을 `localStorage`, `sessionStorage`, IndexedDB에 저장
- 원본이나 OCR 문자열을 오류 추적·분석 도구에 기록
- 원본 파일명을 서버 요청, 로그 또는 가공본 이름에 사용
- OCR 실패 시 원본을 자동으로 업로드

사용자가 취소하거나 화면을 벗어나면 Object URL을 해제하고 OCR Worker를 종료한다.

### 5.2 페이지 변환

이미지는 `createImageBitmap()`으로 디코딩하고 원본 방향이 반영된 Canvas를 만든다.

PDF는 `pdfjs-dist`로 로드한 후 모든 페이지를 Canvas에 렌더링한다. 구현 단순성과 좌표 일관성을
위해 첫 버전은 PDF 텍스트 레이어를 별도로 분석하지 않고 렌더링된 이미지에 동일한 OCR
경로를 적용한다. PDF.js는 페이지 렌더링만 담당한다.

페이지 처리는 메모리 사용량을 줄이기 위해 순차 실행한다.

```text
페이지 렌더링 → OCR → 후보 저장 → 다음 페이지
```

- 렌더링 긴 변은 기본 2,500px을 넘기지 않는다.
- 작은 원본은 확대하지 않는다.
- 암호화되었거나 렌더링할 수 없는 PDF는 수동 처리도 불가능하므로 파일 재선택을 안내한다.
- 페이지별 Canvas와 OCR 중간 이미지는 다음 페이지 처리 전에 해제한다.

### 5.3 로컬 OCR

`tesseract.js` Worker 하나를 redaction 세션 동안 재사용하고 `kor+eng` 언어로 페이지를
순차 인식한다. 문서 픽셀, OCR 문자열과 좌표는 Worker와 메인 스레드 사이에서만 이동한다.

Worker, WebAssembly core와 언어 데이터는 같은 출처에서 제공한다. 외부 CDN을 사용하지 않고
`frontend/public/ocr/` 아래에 필요한 런타임 자산과 출처·버전·해시를 기록한다.

페이지별 OCR 결과는 다음 최소 구조로 변환한다.

```ts
type OcrToken = {
  text: string
  confidence: number
  box: { x: number; y: number; width: number; height: number }
}
```

원본 전체 OCR 문자열은 별도로 보관하지 않는다. 탐지 완료 후 후보와 화면 표시에 필요한
토큰만 유지한다.

### 5.4 토큰 정규화와 행 구성

탐지기는 표시용 원문과 비교용 정규화 문자열을 분리한다.

- 앞뒤 공백 제거
- 여러 공백을 하나로 축소
- 전각 숫자를 ASCII 숫자로 변환
- 번호 검사 시에만 `O/0`, `I/1` 혼동 후보를 생성
- 한글·영문 대소문자 차이를 무시하고 라벨 비교
- Y축이 겹치는 인접 토큰을 같은 행으로 묶음

정규화는 탐지에만 사용하고, 실제 가림 좌표는 원래 OCR 토큰의 좌표를 사용한다.

### 5.5 후보 탐지

탐지는 작은 규칙 집합으로 구성한다. 별도 추상화 계층이나 NER 모델은 만들지 않는다.

#### 형식 기반 규칙

행 안에서 인접한 토큰을 이어 붙이되 각 문자의 원래 토큰 좌표를 유지한다. 다음 형식이
발견되면 해당 문자를 포함하는 모든 토큰의 합집합을 후보 영역으로 만든다.

- 주민·외국인등록번호 형태의 `6자리 + 7자리`
- 국내·국제 전화번호
- 이메일 주소

등록번호는 가능한 경우 날짜 부분과 뒤 첫 자리를 검증한다. 유효성 검사를 통과하지 못해도
`주민번호`, `외국인등록번호`, `Registration No.` 라벨 옆 값이면 후보로 유지한다.

#### 라벨 기반 규칙

다음 라벨을 찾은 후 같은 행의 오른쪽 값을 우선 사용한다. 값이 없으면 바로 다음 행을
검사한다.

```text
성명, Name, 근로자, Employee
사업주, 대표자, Employer, Representative
주소, 소재지, Address
여권, Passport
계좌, 은행, Account, Bank
생년월일, Date of birth, DOB
```

다음 라벨이나 표의 큰 공백을 만나면 값 범위를 끝낸다. 라벨 자체는 가리지 않는다.

#### 후보 신뢰도

| 등급 | 조건 | UI 처리 |
|---|---|---|
| 높음 | 명확한 번호·전화·이메일 형식 또는 라벨과 형식 모두 일치 | 기본 선택 |
| 보통 | 이름·주소처럼 라벨 위치만으로 찾음 | 기본 선택하고 확인 표시 |
| 낮음 | OCR 신뢰도가 낮거나 값 경계가 불분명 | 기본 선택하고 경고 표시 |

개인정보 보호가 목적이므로 낮은 신뢰도 후보도 기본 선택한다. 사용자가 해제할 때에는
“이 영역을 서버로 전송합니다”라는 의미를 명확히 표시한다.

### 5.6 후보 영역 정리

- 같은 값에 속한 토큰 박스를 하나의 사각형으로 합친다.
- 글자 가장자리가 남지 않도록 각 방향에 글자 높이의 15%만큼 여백을 둔다.
- 겹치거나 매우 가까운 같은 종류의 사각형을 합친다.
- 페이지 경계를 벗어난 좌표는 잘라낸다.
- 후보에는 페이지 번호, 종류, 신뢰도, 출처 라벨을 저장한다.

```ts
type RedactionRegion = {
  id: string
  pageIndex: number
  type: 'id' | 'phone' | 'email' | 'name' | 'address' | 'passport' | 'account' | 'birthDate' | 'manual'
  confidence: 'high' | 'medium' | 'low'
  selected: boolean
  box: { x: number; y: number; width: number; height: number }
}
```

## 6. 사용자 검토 화면

redaction은 기존 계약서 업로드 패널과 분석 진행 화면 사이의 한 단계로 추가한다.

```text
idle
  → preparing
  → detecting
  → review
  → exporting
  → uploading
  → 기존 processing/done/error
```

### 화면 구조

- 상단: “문서는 아직 서버에 전송되지 않았습니다” 상태 안내
- 중앙: 확대·축소 가능한 현재 페이지와 선택된 가림 영역
- 하단 또는 우측: 페이지별 후보 목록과 종류·신뢰도
- 하단 고정 동작: 이전 페이지, 다음 페이지, 이 페이지 확인, 가공본 전송

후보 목록과 문서 영역은 서로 연결한다. 목록 항목에 초점을 두면 해당 사각형이 문서에서
강조되고, 사각형을 선택하면 목록 항목으로 이동한다.

### 필수 조작

- 후보 선택·해제
- 빈 영역을 드래그해 수동 사각형 추가
- 사각형 이동·크기 조절·삭제
- 페이지 확대·축소
- 페이지별 확인 완료
- 전체 취소 및 원본 재선택

키보드 사용자는 후보 목록을 체크박스로 조작할 수 있다. 수동 영역은 “가림 영역 추가”로
초기 사각형을 만든 뒤 방향키로 이동하고 `Shift + 방향키`로 크기를 조절할 수 있게 한다.
색만으로 선택·신뢰도·오류 상태를 구분하지 않는다.

화면 문구는 현재 제품처럼 한국어와 영어를 함께 제공한다. 긴 설명 대신 각 단계에서 필요한
한 문장만 노출한다.

```text
민감정보를 기기에서 찾고 있습니다.
Finding sensitive information on this device.

자동으로 찾지 못한 이름, 서명 또는 번호가 없는지 확인해주세요.
Check for any missed names, signatures, or numbers.
```

모든 페이지가 확인되기 전에는 전송 버튼을 비활성화한다. OCR이 아무 후보도 찾지 못한
페이지도 사용자가 직접 확인해야 한다.

## 7. 가림 적용과 파일 생성

사용자가 확인을 마치면 페이지마다 새 Offscreen Canvas 또는 일반 Canvas를 생성한다.

1. 원본 페이지 픽셀을 그린다.
2. 선택된 영역을 완전히 불투명한 검은색 `fillRect`로 덮는다.
3. `canvas.toBlob()`으로 새 JPEG를 만든다.
4. Blob을 다시 디코딩해 가림 영역 중앙과 경계가 불투명한지 확인한다.
5. 익명 파일명을 가진 새 `File` 객체로 변환한다.

블러, 반투명 박스와 모자이크는 사용하지 않는다. 출력은 PDF가 아닌 픽셀 전용 이미지이므로
원본 PDF의 텍스트 레이어, 주석, 첨부와 폼 데이터가 남지 않는다.

출력 기본값은 OCR 가독성과 용량을 함께 고려해 JPEG 품질 0.92로 한다. 검은 글씨 중심의
문서는 PNG보다 JPEG가 서버의 전체 multipart 제한을 맞추기 쉽다. 가림 영역은 압축 후에도
완전한 검은색이 유지되도록 내보내기 직전 적용한다.

```text
document-1-page-1.jpg
document-1-page-2.jpg
```

현재 Spring의 `spring.servlet.multipart.max-request-size`는 11MB다. multipart 오버헤드를
제외한 가공본 총합이 10MB를 넘으면 긴 변과 JPEG 품질을 한 단계 낮춰 다시 생성한다.
최소 OCR 가독성을 보장할 수 없는 크기까지 줄여야 하는 경우에는 자동 업로드하지 않고
문서를 나누어 선택하도록 안내한다. 첫 구현에서는 서버 제한을 변경하지 않는다.

## 8. 전송 전 재검사

가공본을 대상으로 로컬 OCR과 형식 기반 탐지를 한 번 더 실행한다.

- 등록번호, 전화번호 또는 이메일이 다시 발견되면 전송을 중단한다.
- 사용자가 해제한 영역의 값은 재검출 차단 대상에서 제외하되 전송 확인 문구를 표시한다.
- 라벨 기반 이름·주소는 OCR 재검사만으로 안전을 증명할 수 없으므로 최종 이미지 미리보기를
  다시 보여준다.
- 원본 파일명과 원본 `File` 참조가 전송 배열에 없는지 코드 수준에서 확인한다.

재검사를 통과하면 새 이미지 `File[]`만 기존 `analyzeContract()`에 전달한다. 이후 세션 생성,
비동기 분석 시작과 상태 조회는 현재 구현을 그대로 사용한다.

## 9. 오류와 취소 처리

| 상황 | 동작 |
|---|---|
| OCR 런타임·언어 데이터 로딩 실패 | 자동 후보 없이 수동 가림 화면을 제공한다. |
| 개별 페이지 OCR 실패 | 해당 페이지를 미확인 상태로 두고 수동 확인을 요구한다. |
| PDF 암호화·손상 | 업로드하지 않고 지원 가능한 새 파일 선택을 안내한다. |
| 브라우저 메모리 부족 | 작업을 중단하고 더 적은 페이지 또는 낮은 해상도 파일을 안내한다. |
| 가공본 총합 10MB 초과 | 한 번 재압축하고, 그래도 초과하면 문서 분할을 안내한다. |
| 재검사에서 민감정보 발견 | 해당 페이지로 이동하고 후보를 다시 선택한다. |
| 사용자가 취소·화면 이동 | Worker와 Object URL을 정리하고 어떤 파일도 전송하지 않는다. |
| 서버 분석 실패 | 원본이 아니라 현재 가공본만 메모리에 유지해 재시도를 제공한다. |

오류 메시지와 콘솔 로그에는 OCR 문자열, 원본 파일명과 좌표별 원문을 포함하지 않는다.

## 10. 파일별 구현 계획

최소 변경 파일은 다음과 같다. 실제 구현 중 기존 파일에 자연스럽게 합칠 수 있는 작은 타입이나
함수는 새 파일로 분리하지 않는다.

| 파일 | 변경 내용 |
|---|---|
| `frontend/package.json` | `pdfjs-dist`, `tesseract.js` 추가. 탐지 규칙 테스트가 필요하면 Vite와 잘 맞는 최소 테스트 실행 명령을 추가한다. |
| `frontend/package-lock.json` | 설치된 의존성 잠금. |
| `frontend/public/ocr/` | 자체 호스팅할 Worker·WASM·`kor+eng` 언어 데이터와 출처·해시 기록. |
| `frontend/src/components/chatbot/ContractFlow.tsx` | 파일 선택 후 즉시 분석하지 않고 redaction 단계로 진입. |
| `frontend/src/components/chatbot/RedactionReview.tsx` | 페이지 미리보기, 후보 목록, 수동 영역 편집과 확인 UI. |
| `frontend/src/redaction/document.ts` | 이미지 디코딩, PDF 페이지 렌더링과 익명 이미지 생성. |
| `frontend/src/redaction/detect.ts` | OCR 토큰 정규화, 형식·라벨 규칙과 영역 병합. |
| `frontend/src/redaction/ocr.ts` | Tesseract Worker 생명주기와 페이지별 OCR. |
| `frontend/src/redaction/types.ts` | 페이지, OCR 토큰과 가림 영역 타입. |
| `frontend/src/App.tsx` | 가공본이 준비된 뒤에만 `runContractAnalysis()` 호출. 취소 시 정리. |
| `frontend/src/App.css` | 기존 시각 체계를 유지한 검토 화면, 모바일 및 포커스 상태. |
| `SETUP.md` | OCR 자산 준비, 라이선스·해시 확인과 로컬 실행 설명. |

Backend와 AI 파일은 변경하지 않는다. 구현 중 서버 요청 형식이나 허용 MIME 타입을 바꿔야
하는 상황이 확인되면 별도 변경으로 분리한다.

## 11. 구현 순서

### 1단계: 업로드 차단과 수동 가림

1. 파일 선택과 서버 분석 호출을 분리한다.
2. 이미지와 PDF 페이지를 Canvas로 렌더링한다.
3. 수동 사각형 편집과 페이지 확인을 구현한다.
4. 가림을 픽셀에 적용하고 익명 JPEG만 업로드한다.
5. 네트워크에서 원본이 전송되지 않는지 검증한다.

이 단계만으로도 브라우저 redaction의 보안 목적을 달성한다.

### 2단계: 자동 후보 탐지

1. Tesseract Worker와 자체 호스팅 자산을 연결한다.
2. OCR 토큰 정규화와 행 구성을 구현한다.
3. 등록번호·전화번호·이메일 규칙을 테스트 우선으로 추가한다.
4. 이름·주소·여권·계좌·생년월일 라벨 규칙을 추가한다.
5. 후보 병합과 신뢰도 표시를 검증한다.

### 3단계: 재검사와 운영 품질

1. 가공본 형식 기반 재검사를 추가한다.
2. 10MB 제한 내 재인코딩과 실패 안내를 구현한다.
3. 모바일·키보드·다국어 흐름을 실제 브라우저에서 확인한다.
4. 대표 계약서로 탐지 누락과 분석 결과 손실을 측정한다.

## 12. 테스트 계획

### 탐지 규칙 단위 테스트

- 공백과 하이픈이 섞인 등록번호를 하나의 영역으로 탐지
- OCR의 `O/0`, `I/1` 혼동이 있는 라벨 인접 번호 탐지
- 전화번호와 이메일 탐지
- 급여액과 계약기간 날짜를 민감정보로 오탐하지 않음
- `성명`, `Name`, `주소`, `Passport`, `Account`의 오른쪽 값만 선택
- 여러 단어로 된 외국인 이름의 박스 병합
- 겹치는 영역 병합과 페이지 경계 보정

OCR 엔진 자체는 테스트하지 않고 고정된 `OcrToken[]`을 입력해 탐지 규칙만 검증한다.

### 브라우저 통합 검증

- 파일 선택 후 검토 완료 전까지 API 요청이 0건인지 확인
- 취소와 화면 이동 시 API 요청이 발생하지 않는지 확인
- 업로드 multipart가 익명 JPEG만 포함하는지 확인
- 원본 파일명, PDF와 원본 바이트가 요청에 없는지 확인
- 모든 페이지 미확인 상태에서는 전송 버튼이 비활성화되는지 확인
- OCR 실패 시 수동 가림으로 전환되고 원본을 보내지 않는지 확인
- 서버 분석 실패 후 재시도해도 가공본만 재전송하는지 확인

### 시각·접근성 검증

- 360×800 모바일과 1280×800 데스크톱에서 페이지와 동작 버튼 사용 가능
- 확대 상태에서도 후보와 실제 가림 좌표가 일치
- 터치 드래그로 영역 추가·이동 가능
- 키보드만으로 후보 선택, 페이지 이동, 영역 이동·크기 조절과 전송 가능
- 포커스 표시가 보이고 상태를 색상만으로 전달하지 않음
- 한국어·영어 문구가 겹치거나 잘리지 않음
- 브라우저 콘솔에 OCR 내용과 파일명이 출력되지 않음

### 완료 전 명령

```bash
cd frontend
npm run lint
npm run build

cd ..
git diff --check
git status --short
```

규칙 테스트 명령은 구현 시 `frontend/package.json`에 등록하고 위 검증에 포함한다.

## 13. 완료 기준

- 원본 선택부터 사용자 확인 완료까지 서버 또는 제3자에게 문서 데이터 요청이 발생하지 않는다.
- 서버 요청에는 익명화된 JPEG 가공본만 포함된다.
- 가림 영역의 원문 픽셀, PDF 텍스트 레이어와 원본 메타데이터가 가공본에 남지 않는다.
- 등록번호·전화번호·이메일 테스트 픽스처를 탐지하고 급여·계약일을 오탐하지 않는다.
- 자동 탐지가 실패하거나 후보가 0개여도 페이지별 사용자 확인을 강제한다.
- 사용자가 누락 영역을 수동으로 추가하고 자동 후보를 수정할 수 있다.
- 현재 계약 분석 API의 성공·진행·실패 흐름이 가공본에서도 동일하게 동작한다.
- 대표 문서에서 가림 전후의 급여·근로시간·공제 진단 결과가 유지된다.
- lint, build, 탐지 규칙 테스트와 실제 브라우저 네트워크·접근성 검증이 통과한다.

## 14. 보안 한계

브라우저 redaction은 서버와 외부 OCR 제공자가 원본을 받지 않게 하지만 다음 위협까지
제거하지는 않는다.

- 악성 브라우저 확장 프로그램
- 손상되거나 변조된 프론트엔드 배포 파일
- 사용자의 기기 자체가 침해된 경우
- 자동 탐지와 사용자 검토가 모두 놓친 민감정보

따라서 HTTPS, 제한된 Content Security Policy, 정적 자산 무결성 관리, 서버의 접근 제어·보관
기간 제한과 로그 최소화는 별도로 유지해야 한다. 서버 측 redaction은 원본 수신을 막지는
못하지만 이후 저장소·OCR·LLM으로 전달되는 범위를 줄이는 방어선으로 사용할 수 있다.
